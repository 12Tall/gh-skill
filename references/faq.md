# 常见问题与已确认约定

这里整理可复用的结论，不保存聊天原文或其他项目的细节。

- **怎么启用？** 推荐按 [README](../README.md) 用 `pi install git:github.com/12Tall/gh-skill` 全局安装，重载后在任意项目用 `/skill:gh-skill` 调用；默认包含自动压缩扩展，可在 `pi config` 禁用。要让 Pi 默认在提交前自审，将 README 的指引追加到 `~/.pi/agent/AGENTS.md`（所有项目）或项目的 `AGENTS.md`（仅该项目）。这不是 Git hook，不拦截手动提交。
- **怎么更新 Skill？** 全局安装在终端执行 `pi update git:github.com/12Tall/gh-skill`，成功后在 Pi 会话内执行 `/reload` 或重启；无需重新克隆。固定标签或提交不会自动升级到新版本。手动项目克隆则执行 `git -C .agents/skills/gh-skill pull --ff-only`。完整步骤见 [README](../README.md)。注意不带参数的 `pi update` 更新的是 Pi 本身。
- **会自动用 subagent 吗？** 不会。默认由主 Agent 轻量推进；明确任务不重复确认方案和修改，验证默认包含在授权内，遇到关键歧义或授权门槛才暂停，也可要求每一步确认。委派前须确认分工和读写范围，子 Agent 不得扩大授权、自行提交或 push、继续委派；主 Agent 必须核验结果。本 Skill 不提供 subagent 工具，也不提供权限隔离。每项修改任务完成后会明确询问是否提交、是否 push，已授权的操作不重复询问。
- **新仓库用什么分支？** 默认 `master`，用户可以覆盖；已有仓库按实际默认分支操作，不擅自改名。
- **从 Issue 做到哪一步？** 仅要求实现时，完成本地修改和验证就停。明确要求 Draft PR 也不等于同意提交：先汇报改动与验证结果，获得确认后才创建或修改提交；未解决的本地失败不默认推送。合并和生产部署单独确认。
- **怎么判断设计是否过度耦合？** 先写验收条件，分开职责。必须一起变化的规则由负责它的模块统一维护；碰巧相等但能独立变化的值保持独立。重复的是判断逻辑时，优先共享函数。
- **修改函数能改签名吗？** 默认保持签名和行为契约兼容。必须破坏兼容时先查调用方、接口、Mock、配置和文档，统一迁移已知受影响用法并测试。复杂迁移优先用新实现加旧入口适配；简单内部重构不强制新建函数。公开接口或外部调用方未明确时，不能仅凭本地零引用和新函数测试通过就删旧入口，详见[函数兼容与迁移规则](development.md#function-compatibility-and-migration)。
- **哪些任务要验证？** 主线、支线和临时任务都默认执行相关验证，只有明确要求跳过才豁免。验证不需要重复确认，但不扩大外部访问或高风险操作权限。缺少工具或权限时报告未验证项；静态检查和场景核对不能冒充真实 Agent 行为测试。
- **提交前看什么？** 按 [开发清单](development.md) 查暂存差异、遗漏的文件、回归风险和测试。先复现问题，再做最小修复。实质问题或验证受阻就先汇报，不提交。
- **如何用 ReAct？** 不引入框架。按「选工具 → 执行 → 观察结果 → 决定下一步」推进。能用工具或确定性代码核验的事实，不靠模型猜测。比如 [诊断 CI](actions.md) 时，报告当前 PR 提交和运行链接，不把旧失败或待定状态当成当前结果。
- **新要求如何整理、长对话怎么回主线？** 自动区分咨询、执行任务和长期约束；保持一个当前主线目标和简短支线清单。明确的小任务不反复问，关键目标不清、范围扩大或优先级冲突时逐步澄清。讨论不自动变成任务，切换时记住主线停点，收尾说明下一步。只在切换、遇阻和完成时汇报状态，不默认创建任务文件。详见[轻量需求整理规则](development.md#lightweight-task-intake)。
- **可以访问项目外资源吗？** 先确认目标和用途，读取也一样。用户明确指定并要求访问的资源，只在所述范围内获授权。凭据、项目里的链接或一句「继续」不扩大授权；已安装 Skill 自带的参考资料除外。
