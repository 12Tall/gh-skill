# Platform authentication

If the task only needs Git and its SSH or HTTPS transport is already working, do not require a platform API token. For new API login setup, default to a user-created, scoped personal access token (PAT) for the exact instance and task. Keep working logins unless the user asks to replace them. Never ask for a token in chat, echo it, put it in a command argument or repository file, or copy it between hosts. Prefer local interactive credential entry or a credential store. Check the selected host/account without displaying tokens. Credentials and scopes are not user authorization for a particular operation.

Before every new token setup, replacement, or scope change, show the user the exact instance, intended repositories or resource limits, task, and permission checklist. Label each permission as required now or optional for a named later action, and disclose any scope broader than the task. Ask the user to choose the scope or cancel before proceeding with login or configuration. Never treat approval for reading as approval for write scopes; if a request fails for lack of permission, explain the smallest candidate change and ask again.

| Platform | Read-only scope | Issue-to-PR/MR writes (separate approval) |
| --- | --- | --- |
| GitHub (`gh`) | Prefer a fine-grained token limited to selected repositories: Metadata read (automatic), Issues read, Pull requests read, Actions read as needed. Add Checks or Commit statuses read only when required by the queried endpoint. | Pull requests write to open PRs; Issues write only for Issue updates; Contents write for HTTPS Git push (not needed for SSH push); Workflows write when changing workflow files via HTTPS, if required. Actions write only for authorized Actions mutations. Cross-repository Fork access and organization approval may restrict fine-grained tokens; stop and explain rather than defaulting to a classic token. |
| Gitea (`tea`) | `read:repository` for repository metadata and repository endpoints as supported by the instance; `read:issue` for Issue endpoints that require it. Permit private resources for a private repository. Verify CI endpoint scopes on the actual instance before expanding access. | `write:repository` for PR creation where supported; `write:issue` only for Issue mutations. A Git push separately needs write access on the verified source repository. Never request `admin` for this flow. |
| GitLab (`glab`, planned) | `read_api` for read-only API operations. `read_repository` is for Git over HTTPS and is not a substitute for `read_api`. | MR creation with a personal access token generally needs `api`, which is broader than MR creation. Explain that before the user approves; prefer a suitably scoped project token where available and compatible. `write_repository` covers Git push over HTTPS, not MR creation. SSH push uses separate Git credentials. |

Create tokens in the target instance's settings: GitHub **Settings → Developer settings → Personal access tokens → Fine-grained tokens**; Gitea **Settings → Applications**; GitLab **Edit profile → Access tokens** (labels may vary by version). Use an expiry and the narrowest available resource selection. If a CLI rejects an otherwise suitable token during login, report the limitation rather than automatically requesting broader scopes. Gitea's `tea login add` can take a token interactively; do not opt into its Git credential helper by default.
