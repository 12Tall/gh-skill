# GitLab: limited authentication and runner preview

This limited preview covers authentication, read-only project/Issue/MR/pipeline queries, and runner availability guidance. On GitLab.com, `glab` verified PAT authentication and read-only queries on an official public project, including a merged-results pipeline. A read of private project metadata also passed with an existing broader PAT; this does not validate a dedicated `read_api`-only token. Runner behavior has not been verified. The separately approved same-repository write smoke test also passed on GitLab.com: SSH push, `glab mr create --draft`, API verification of draft state, branches and head SHA, then closure without merge. That evidence does not enable Issue-to-MR automation, Fork writes, GitLab CI mutations, or runner management.

- For an authorized GitLab API check, use the intended instance's existing PAT login, or follow the [token permissions guide](authentication.md) for a new login. Prefer `read_api` for read-only checks. Before configuring a token, show the exact instance, project and requested scopes, then wait for the user to choose. For a new PAT, include an explicit expiration date in the approval checklist. Default to 365 days if the instance permits it, subject to the user's confirmation of the actual expiration date; honor stricter instance limits or a shorter user-selected lifetime. Do not proceed with a new token until the user has confirmed its scope and expiration. If a token expires, ask before configuring a replacement. Do not request `api` or Git write scopes for read-only verification. Do not require a PAT for Git-only work if Git transport already works.
- Verify token access with an explicitly targeted, authorized read of project metadata, not a write or pipeline trigger. A failed read does not justify expanding the token scope. Reuse a working login; never display token values.
- For CI, use the requested MR's detail and MR-specific pipeline list, not the latest run on a branch. Recheck the current head and linked pipeline after reading their details. For a merged-results pipeline with a different SHA, verify the MR merge ref and that the temporary merge commit includes the current MR head (for example, as a parent). Without reliable attribution, report it as unconfirmed rather than reporting success for the current revision.
- Consider eligible instance, group, and project runners. If none are available, leave runner-dependent execution unconfigured and explain the limitation. If availability cannot be established, report it as unknown; an empty list or insufficient API visibility is not proof of absence. Authorized reads of existing pipelines are separate from runner availability.
- If the user wants to add runner support, remind them to update this Skill's GitLab guidance and validate a real pipeline on the intended instance. Do not install, register, enable, or substitute a runner without separate scope and approval.
